# CreditIQ

A credit risk model development workbench: build a probability-of-default model
and a loss-given-default model on account-month panel data, project them through
Federal Reserve supervisory scenarios, and read the expected credit loss that
falls out.

**Everything in this application is synthetic.** No client data, no client
figures, no client logo. The panels are generated locally from a fixed seed —
see *Reproducing the data* below.

**Nothing here is a validated model.** It demonstrates a modelling capability. It
carries no regulatory approval, has not been independently validated, and makes
no claim of SR 11-7 compliance.

## Quick start

```bash
make setup     # create the venv, install dependencies, build the panels (~3 min)
make dev       # run the backend and the frontend together
```

`make setup` is needed once. The panels are NOT included in this archive —
they are 233 MB and they are reproducible, so `make setup` generates them.

Then open <http://localhost:5173>.

`make help` lists every target.

## Reproducing the data

The panels are not committed as a fixture — they are **generated**, and the
generator is deterministic. One fixed seed per portfolio:

| Portfolio | Seed | Accounts | Account-months | Defaults |
|---|---|---|---|---|
| Consumer installment | `20260819` | 50,000 | 1,509,093 | 5,254 |
| Residential mortgage | `20260820` | 55,000 | 2,869,721 | 4,631 |
| Commercial real estate | `20260821` | 45,000 | 1,793,840 | 2,385 |

To rebuild them:

```bash
make data
```

It takes about ten seconds and **overwrites `data/synthetic/`**. The same seed
produces the same bytes: rebuilding and comparing checksums gives an identical
file, which is the property that makes every number in the application
reproducible from source rather than from a stored artefact.

```bash
# verify determinism for yourself
md5 data/synthetic/mortgage_panel.parquet
make data
md5 data/synthetic/mortgage_panel.parquet   # identical
```

The seeds live in `backend/creditiq/data/build.py` (`SEEDS`). Portfolio sizes
and every distributional assumption live in `backend/creditiq/data/portfolios.py`.

### What the generator produces

Each portfolio gets a monthly panel of account observations from January 2008 to
December 2025, plus a static account table. The generative structure — the
copula, the frailty term, the delinquency Markov chain, the vintage quality
drift — is documented in `docs/GENERATIVE_TRUTH.md`, which the build regenerates
so it can never fall out of step with the code.

The 2008–2010 default spike is **emergent**, not painted on: it comes from the
macro drivers moving through the crisis, so a model fitted on the panel picks it
up rather than being told about it.

Columns beginning `_truth` are the generator's latent variables. They are
stripped at write time and again at load time, because a latent variable
reaching the model surface would produce a perfect model in front of a client.

### Macroeconomic data

The macro series are real Federal Reserve Economic Data, cached to
`data/mev_cache/` and committed. The application reads the cache and never calls
the network.

To refresh the cache you need a free FRED API key and a network connection:

```bash
export FRED_API_KEY=...    # never commit this
make fred
```

The key is read from the environment, is never written to disk, and is not
logged. `.gitignore` excludes `.env`.

## Between demos

```bash
make reset
```

Deletes every saved model version and regenerates the panels, so the
application starts from a blank slate. Because the generator is seeded, the
regenerated panels are byte-identical to the ones they replace — resetting
changes what is SAVED, never what the models are fitted on.

Restart the backend afterwards to clear its in-process caches.

## If this arrived as an email attachment

Corporate mail gateways apply three separate rules to archives, and this project
has tripped all of them:

| Rule | What triggered it |
|---|---|
| No JavaScript inside an archive | `tailwind.config.js`, `postcss.config.js` |
| Contents inspected, not the extension | renaming the `.zip` changed nothing |
| A cap on the FILE COUNT in an archive | `550 5.7.0 file count in archive Violation` |

The first is fixed for good: this project ships no JavaScript configuration at
all. `frontend/tailwind.config.ts` is TypeScript, which Tailwind reads natively,
and PostCSS is configured inline in `frontend/vite.config.ts`.

The third cannot be fixed by repacking — the project has more files than the
gateway allows in any archive. So it can be sent as a **single text bundle**,
which is not an archive and is not subject to any of these rules:

```bash
python3 tools/bundle.py pack     > creditiq-bundle.txt   # ~2 MB, one file
python3 tools/bundle.py unpacker > unpack.py             # ~1 KB
```

The recipient runs:

```bash
python3 unpack.py creditiq-bundle.txt
cd creditiq && make setup && make dev
```

The bundle is plain readable text — sources verbatim between markers, binaries
base64 and labelled as such — so a gateway or a reviewer can see exactly what is
in it, which is not true of a zip. `unpack.py` writes files and does nothing
else: no network, no shell, and it refuses to write outside its destination.

Between organisations, a Google Drive, SharePoint or OneDrive link avoids all of
this and needs no change here.
