# End-to-end workflow run — responsiveness and UX notes

2026-09-20. Full start-to-finish exercise, driven in Chrome: three demo books
plus one ingested 22M-row auto tape (Santander Book_noLGD), each taken through
variable selection → PD fit → severity → projection → save → promote, ending
with the four-book roll-up ($16B exposure, $611M baseline, $1.1B severely
adverse).

## Fixed during this run

1. Portfolio switcher collapses past 3 books (row no longer overflows).
2. Ingest no longer clears the whole store — the minute of dead skeletons
   after adding a tape is gone; book list serves from the ingest record.
3. The fingerprint watchdog no longer reloads the app for changes this tab
   caused (ingest / remap are "blessed").
4. Failed requests now show error cards with retry — never a skeleton that
   pulses forever. GETs carry timeouts; a server-down banner shows and
   self-clears.
5. Live ingest progress: stage + row counts + elapsed, polled.
6. Tape form: dropzone collapses to a file row after inspection; the disabled
   button lists exactly what is still needed.
7. Panel loads are single-flight per book (concurrent first-touch requests
   used to load the same 400MB parquet 3–4× in parallel and starve the
   server, health probe included).
8. LGD population: severity is fitted on defaults with an OBSERVED severity.
   On a tape where recoveries are reported for a subset, NaN severities
   poisoned the fit (mean displayed 0.0%, all coefficients NaN). Synthetic
   books unaffected (filter is a no-op there).

## Open improvements, prioritized

1. **Leakage flags don't fire on ingested books.** On the real tape the
   top-IV candidates were the outcome restated — zeroBalanceCode (IV 5.2),
   chargedoffPrincipalAmount (3.8), currentDelinquencyStatus (9.8) — offered
   as ordinary candidates with no flag. The detector keys on the synthetic
   books' column names. It should flag by structure: IV far above the field,
   values populated only at/after the event, near-perfect separation. This is
   the highest-credibility item: a screenshot of a "model" built on
   zeroBalanceCode would be embarrassing in front of a bank.
2. **After "Run the screening", nothing moves on screen.** The button greys
   out but the user must know to click Leaderboard to see progress. Flip to
   the Leaderboard view on start (the LGD search already does this on
   completion).
3. **Book-aware defaults.** The workbench's out-of-time date is hardcoded
   to 2023-01 even though ingestion asks for and stores the book's own OOT
   date; on the 2022–2026 tape the default put 92% of the panel out of time.
   Same for the empty spec's macro terms (synthetic books get presets,
   ingested books get none).
4. **First touch of a big book shows plain skeletons for 30–60s.** The
   ingest's staged-progress treatment should extend to the first panel load
   ("Loading the panel · 22.2M rows"), and /prepare could also warm the
   analysis frame in the background right after ingestion.
5. **"Server is not responding" banner during legitimate heavy work.** The
   health probe starves while a big panel loads, so the banner cries wolf.
   Single-flight (#7 above) mostly fixes the starvation; if it still appears,
   soften to "The server is busy or unreachable."
6. **Stale browser state after a server reset.** An old tab showed LGD
   "Calibrated" from its local cache and the CTA skipped to "Save this
   model". Cached fit results should be validated against the server the way
   loaded-version markers already are.
7. One renderer freeze (~45s, self-recovered) was observed during the
   concurrent-load storm; not reproduced after the single-flight fix. Watch.

## How saving work actually functions (the "configs" question)

The unit of record is the **saved version**: Save this model on the Versions
surface stores the complete specification server-side (versions/*.json),
replayable to the same numbers, exportable, and promotable to champion — the
roll-up reads champions. That is "saving your work" for anything fitted.

Below that: **Screen configurations** can be saved by name on the Setup pane
(reusable search setups); **drafts** (ticked variables, shortlists, unfitted
edits) persist in the browser store per book and survive restarts of both
servers, but live only in that browser profile. The gap, if one is worth
closing: a named server-side snapshot of a draft-in-progress, so half-built
work moves across machines. Everything fitted and saved already does.
